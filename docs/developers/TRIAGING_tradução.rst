Triagem de novas issues/PRs no GitHub =================================== Este documento descreve as etapas que a comunidade Hoodie segue para realizar a triagem de *issues* (problemas/tarefas). As etiquetas (*labels*) são usadas posteriormente para a `atribuição de tarefas <#assigning-work>`__. Se você deseja ajudar na organização das *issues*, `deixe um comentário aqui <https://github.com/hoodiehq/discussion/issues/50>`__ solicitando a entrada na equipe de triagem. Processo de Triagem ------------------- Este processo baseia-se na ideia de minimizar o impacto negativo para o usuário (*user pain*), conforme apresentado `neste post de blog <http://www.lostgarden.com/2008/05/improving-bug-triage-with-user-pain.html>`__. 1. Abra a lista de *issues* `ainda não triadas <https://github.com/hoodiehq/hoodie/issues>`__ - Ordene pela data de envio, exibindo as mais recentes primeiro. - Não é necessário seguir uma ordem específica; sinta-se à vontade para escolher as *issues* que preferir. - Você também pode realizar a triagem de *issues* mais antigas. - Fique à vontade para triar quantas desejar. 2. Atribua a si mesmo(a): Escolha uma *issue* que não esteja atribuída a ninguém e designe-a para você. 3. Está compreensível? – Verifique se a descrição da solicitação está clara. - Caso não esteja, `feche a issue <#closing-an-issue-or-pr>`__ seguindo as instruções abaixo e prossiga para a etapa final.

4. Duplicado? - Se você já viu este problema antes, `feche-o <#closing-an-issue-or-pr>`__ e vá para a última etapa. - Verifique se há comentários que apontam para um item duplicado. Se houver, confirme se é realmente uma duplicata, `feche-o <#closing-an-issue-or-pr>`__ e vá para a última etapa. 5. Bugs: - Adicione a etiqueta ``Type: Bug``. - É reproduzível? – Os passos para reproduzir o bug estão claros? Se não estiverem, peça esclarecimentos. Se não houver resposta após uma semana, `feche-o <#closing-an-issue-or-pr>`__. - É reproduzível na branch `master`? 6. Não são bugs: - Adicione a etiqueta ``Type: Feature``, ``Type: Chore`` ou ``Type: Perf``. - Pertence ao núcleo (core)? – Frequentemente, novas funcionalidades devem ser implementadas como um plugin, em vez de serem adicionadas ao núcleo. Se não pertencer ao núcleo, `feche-o <#closing-an-issue-or-pr>`__ e vá para a última etapa. - Adicione a etiqueta ``needs: breaking change``, se necessário. - Adicione a etiqueta ``needs: public api``, caso o problema exija a introdução de uma nova API pública. 7. Adicione a etiqueta ``frequency: *`` – Com que frequência esse problema ocorre? Quantos desenvolvedores ele afeta? - `low` (baixa) – problema pouco comum que afeta um pequeno grupo de desenvolvedores. - `moderate` (moderada) – impacta um padrão de uso comum. - `high` (alta) – impacta a maioria ou a totalidade das aplicações Hoodie. 8. Adicione a etiqueta ``severity: *`` – Qual a gravidade do problema? - `regression` (regressão) - `memory leak` (vazamento de memória) - `broken expected use` (uso esperado comprometido) – torna difícil ou impossível para um desenvolvedor que utiliza o Hoodie realizar algo que o framework deveria permitir. - `confusing` (confuso) – comportamento inesperado ou inconsistente; difícil de depurar. - `inconvenience` (inconveniente) – resulta em código pouco elegante ou excesso de código repetitivo (*boilerplate*) nas aplicações. 9. Adicione a etiqueta ``starter`` – Estes problemas são boas oportunidades para contribuições (PRs) da comunidade *open source*. Aplique a *issues* nas quais o problema e a solução estejam bem definidos nos comentários e que não sejam excessivamente complexas. 10. Rótulo ``milestone: *`` – Atribua um *milestone* (marco): - Backlog – correções e funcionalidades triadas; deve ser a opção padrão. - x.y.z – por exemplo, 0.3.0

Encerrando uma Issue ou PR -------------------------- Somos gratos a todos que dedicam seu tempo para enviar uma *issue*, mesmo que, no final, decidamos não tomar nenhuma providência a respeito. Seja gentil e respeitoso ao encerrar *issues*. Certifique-se de seguir o `código de conduta <http://hood.ie/code-of-conduct.html>`__. 1. Agradeça sempre à pessoa que enviou a *issue*. 2. Se for uma duplicata, inclua um link para a *issue* mais antiga ou mais detalhada que substitui a que você está encerrando. 3. Informe à pessoa se existe alguma forma de ela dar continuidade ao assunto. - Caso a *issue* não esteja clara ou não seja possível reproduzi-la, avise que você a reabrirá se a pessoa puder fornecer mais esclarecimentos ou um exemplo melhor. Sugira o uso do `jsbin <https://jsbin.com>`__ para criar exemplos. Fique atento às notificações e dê retorno caso a pessoa forneça os esclarecimentos necessários. :) - Se for apropriado, sugira a implementação da funcionalidade como um módulo de terceiros. Em caso de dúvida, pergunte a um membro da equipe principal (*core team*) como proceder. **Exemplo:** Obrigado por enviar esta *issue*! Infelizmente, acreditamos que essa funcionalidade não faz parte do núcleo (*core*) do projeto. A boa notícia é que você pode implementá-la como um *plugin* e publicá-la no npm utilizando a palavra-chave ``hoodie-plugin``. Atribuição de Tarefas --------------------- Esses critérios são usados ​​para calcular uma pontuação de "impacto para o usuário" (*user pain*). As tarefas são atribuídas semanalmente aos membros da equipe principal, começando pelas de maior impacto e seguindo em ordem decrescente até as de menor impacto. :: impacto = gravidade × frequência **gravidade:** - regressão (5) - vazamento de memória (*memory leak*) (4) - falha em um uso esperado (3) - confuso (2) - inconveniente (1) **frequência:** - baixa (1) - moderada (2) - alta (3) **Observação:** Regressões e vazamentos de memória devem, quase sempre, ser classificados com ``frequência: alta``.
